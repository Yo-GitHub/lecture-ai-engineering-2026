## 宿題

- **取り組んだレベル：基礎**

### やったこと

`app/config.py` の `RAG_TOP_K` を5から3に変更し、通常のベクトル検索で取得するページ数を減らした。

変更前後で同じ質問を `--trace` 付きで実行し、回答内容、引用根拠、ツール呼び出し、実行時間、トークン数、推定費用を比較した。

### 比較した質問と固定条件

質問：

「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」

- モデル：gemini-3.5-flash-lite
- 対象資料：第1〜3回の本講義214ページ
- 検索方式：通常のベクトル検索
- 変更箇所：`RAG_TOP_K` のみ（5 → 3）

### 比較結果

| 項目 | 変更前（5件） | 変更後（3件） |
|---|---|---|
| 回答内容 | LoRAは本体を固定しA・Bを学習。QLoRAは4bit量子化を追加 | 同じ内容を回答 |
| 引用根拠 | 第2回 PDF p.51、p.52 | 第2回 PDF p.51、p.52 |
| ツール呼び出し | search_materials 1回 | search_materials 1回 |
| 検索語 | LoRA 固定 学習 QLoRA 加える | 同じ |
| 実行時間 | 13.61秒 | 8.48秒 |
| 入力トークン | 3,028 | 2,079 |
| 出力トークン | 190 | 174 |
| モデル応答回数 | 2回 | 2回 |
| 推定費用 | $0.001383 | $0.001059 |

検索件数を5から3に減らした結果、今回の実行では以下の変化があった。

- 実行時間：約37.7%短縮
- 入力トークン数：約31.3%削減
- 推定費用：約23.4%削減

回答内容と引用根拠には大きな変化がなく、必要な情報は取得できていた。

### 改善した例と残る失敗・制約

今回のLoRA・QLoRAに関する質問では、検索件数を減らしても回答に必要な情報を取得でき、入力トークン数と推定費用を削減できた。

一方、複数のページに根拠が分散している質問では、検索件数を減らすことで必要な情報が取得できなくなる可能性がある。

また、各条件1回ずつの実行結果であるため、応答時間や費用の差が常に再現されるとは限らない。

### 気づき・疑問

検索件数を増やせば回答がよくなるとは限らず、質問に必要な根拠を適切に取得することが重要だと分かった。

今回は3件でも十分だったが、質問の種類によって適切な検索件数が変わる可能性があるため、実際の用途では複数の質問を使って評価する必要があると感じた。
